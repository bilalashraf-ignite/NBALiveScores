  <decision>Theme Toggle Implementation Strategy</decision>
  <context>
**Background:**
- UAT Test 12 failed: "There is no button that changes the theme"
- UAT Test 13 passed: Dark mode works via system preference detection
- Original requirements (REQUIREMENTS.md) have NO requirement for manual theme toggle
- Phase 5 planning (05-CONTEXT.md) made NO mention of theme toggle feature
- Current implementation uses CSS `@media (prefers-color-scheme: dark)` with Tailwind `dark:` classes
- All components properly support dark mode (game cards, modals, tables, badges)

**Root Cause:**
UAT Test 12 introduced new expectation not in original v1.0 requirements.

**Trade-offs:**

**Option A (System-based only):**
- Pros: Already working, follows OS preference, zero code/bundle cost, standard pattern for many apps
- Cons: Users can't override system preference, UAT Test 12 considered "failed"

**Option B (Add manual toggle):**
- Pros: User control, can toggle without changing OS settings, meets UAT Test 12 expectation
- Cons: +8-12KB bundle (next-themes), requires refactoring all components to use ThemeProvider, adds toggle button to UI, localStorage persistence, more complex than needed for v1.0

**Implementation effort if Option B:**
- Install next-themes library
- Create ThemeProvider in app layout
- Add toggle button to header/navbar (requires creating header component)
- Update all dark: classes to work with next-themes (likely compatible as-is)
- Test localStorage persistence and SSR hydration
- Estimated: 1-2 hours implementation + testing

**User expectation analysis:**
Test 12 asks: "On both light and dark mode (check system preferences), all text on game cards should be clearly readable."
This suggests the tester ALREADY used system preferences to test both modes. The "no toggle button" complaint may be misunderstanding of how dark mode was implemented.
  </context>

      <name>Keep System-Based Dark Mode (No Manual Toggle)</name>
      <pros>
- Already implemented and working (Test 13 passed)
- Follows user's OS preference automatically
- Zero additional code or bundle size
- Standard pattern (GitHub, Twitter, many modern apps use system preference)
- Simpler UX - one less setting for users to manage
      </pros>
      <cons>
- UAT Test 12 remains "failed" (though Test 13 passed)
- Users who want light mode on dark OS (or vice versa) cannot override
- Some users may expect manual control
      </cons>
      <if_chosen>

- Document in REQUIREMENTS.md that dark mode follows system preference (design decision)
- No code changes needed
      </if_chosen>
    </option>
    <option id="add-toggle">
      <name>Add Manual Theme Toggle Button</name>
      <pros>
- Gives users control independent of OS settings
- Meets UAT Test 12 expectation
- Common pattern in content-heavy apps (news sites, documentation)
- Allows testing both modes without changing OS settings
      </pros>
      <cons>
- +8-12KB bundle size (next-themes library)
- Requires creating header/navbar component for toggle button
- Adds UI complexity (where to place toggle, icon choice)
- Requires localStorage and SSR hydration handling
- More code to maintain
      </cons>
      <if_chosen>
- Create new plan (05-08-PLAN.md) for implementation

- Verify all existing dark: classes work with next-themes
- Update UAT Test 12 to test manual toggle functionality
      </if_chosen>
    </option>
    <option id="hybrid">
      <name>Hybrid: System Default + Manual Override</name>
      <pros>
- Best of both worlds - respects OS preference by default, allows override

- Accommodates both user types
      </pros>
      <cons>

      </cons>

- Default to "system" mode
- Toggle button cycles through all three states
